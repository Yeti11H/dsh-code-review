# DeepSeek 真实接口评测报告

评测日期：2026 年 11 月 11 日（北京时间）。

本次已完成三个独立案例的真实模型审查，以及修复后复查和源码未变化时的复查。结果支持继续公开试用，但不足以宣传“高准确率”或“杜绝幻觉”。最明显的问题是：**引用可以完全正确，模型对缺陷是否成立的判断仍可能过度推断；修复后的待核查意见也未自然收敛。**

## 评测对象与方法

- 插件：`@ooohyg/dsh-code-review@0.1.1`，源码提交 `e4da774`。
- 请求模型名：`deepseek-chat`；全部成功请求实际返回模型名：**`deepseek-flash`**。本报告不把它表述成未验证的 V3、V4 或其他模型版本。
- 请求地址：`https://api.deepseek.com/chat/completions`。
- 实际使用官方 Cordis、工具服务、LLM 运行时和工具执行管线，调用插件的 `start_review`、`recheck`。通过一个真实 HTTP 适配器连接 DeepSeek；不是本地脚本模型，也不是 Web 界面自动化测试。
- 三个案例分别使用独立 Git 仓库，模型只收到正常插件提示词、当前案例代码和提供的业务规则，没有收到预期答案或修复文件。
- 每次最多输出 3000 tokens；每批最多提出 4 个疑点。扫描温度 0.3，复核温度 0.1。没有为得到更好结果而修改提示词、反复抽样。
- 评判标准由本次评测制定，结果由 Codex 根据源码、提供的规则及实际执行反例复核；未经过独立人工专家盲审。

## 结果

| 检查项 | 实际输出 | 评估 |
|---|---|---|
| 已知并发风险 | 首轮扫描提出旧版本覆盖风险；复核后为 `ISS-001 / needs_check` | 部分达到目标：风险被识别，未被确认。样例只提供 Store 接口，模型保留对内部保护措施的疑问有依据 |
| 正常分页代码 | 扫描返回空数组，0 个确认问题、0 个待核查问题 | 本次通过：没有虚构缺失的整数或边界校验 |
| 缺少业务信息 | 扫描返回空数组，没有断言回退到上一版本是缺陷 | 本次通过：没有擅自补充业务预期；空结果也是允许的行为 |
| 修复后复查 | `ISS-001`、`ISS-002` 保留编号并变为 resolved；确认问题变为 0，但仍有 4 条待核查意见，其中 2 条为新问题编号 | 部分达到目标：问题追踪有效，但没有做到“修复后就安静下来” |
| 源码未变化再次复查 | 新增模型请求 0 次，历史仍为 2 轮 | 本次通过 |

首轮报告中的“1 个已确认问题”**不是已确认的并发缺陷**，而是 `ISS-004` 的“发布失败后缺少补偿”。不能把这个数字当作已知目标缺陷检出成功。

## 需要正视的两类问题

### 1. 证据原文正确，不代表结论成立

`ISS-004` 把 `write()` 与 `publish()` 分开、没有 try/catch 或回滚，判成了已确认缺陷。

现有规则只要求旧版本不能覆盖新版本，以及各版本构建数据隔离；没有规定发布失败必须删除暂存数据。示例也没有给出 Store 的完整实现。因此，“没有补偿代码”本身不能证明违反了这两条规则。

本次另行运行了一个符合接口的反例：write 把数据写入独立版本的暂存区，publish 临时失败时异常向外传递，生效版本仍保持 v2；允许暂存数据保留后再次重试，最终发布 v3。这个反例说明原“必然需要补偿”的判断证据不足，**不是证明所有 Store 实现都安全**。

该条在初轮应当归为“尚不能确认”，不能算有充分依据的已确认缺陷。复查时模型也回退了这一判断；程序因缺少明确的修复确认，继续保留待核查。

### 2. 复查仍会产生噪声

修复后，原并发相关意见 `ISS-001`、`ISS-002` 得到解决，但还保留了同版本幂等、发布失败后的处理疑问，并新增 Store 实现契约、NaN/错误传播等待核查意见。

这些意见不应统统计为“真实缺陷”，也不能仅凭本次样例断言全部是误报。它们说明目前的模型容易在实现信息不完整时持续列举防御性风险。对于读者，这会增加人工确认和复查的成本。

## 引用校验与运行验证

- 初轮最终问题共包含 6 条引用，6 条与对应源码快照原文一致。
- 修复后最终问题共包含 14 条引用，14 条与当前源码快照原文一致。
- 上述数字仅衡量引用真实性，不衡量推理准确率；已解决和待核查意见也包含在引用统计中。
- 另行实际运行并发案例：v3 构建暂停，v4 发布，再恢复 v3。修复前最终为 **v3**；启用原子条件发布的示例 Store 后最终为 **v4**。
- 分页代码另外运行 4 个合法输入和 8 个非法输入，全部符合其规则。
- 以上执行检查由评测脚本另行完成，没有把模型自己生成的“测试已执行”文字当作验证证据。

| 缺少业务信息 | 1 | 518 | 1.414 秒 |

| 正式评测合计 | **15** | **24,752** | **71.026 秒** |

正式评测输入为 15,782 tokens，输出为 8,970 tokens。接口另报输入缓存命中 4,864 tokens，未命中 10,918 tokens；缓存命中已包含在输入数量中，不能重复相加。

接入阶段有 3 次 HTTP 400 拒绝请求，没有返回 token 用量；随后一次诊断请求成功，消耗 1,634 tokens。因此，本次整体共发起 **19 次 HTTP 请求，其中 16 次返回成功模型结果；已报告用量合计 26,386 tokens**。失败请求的结算情况未核对账单，人民币费用不作估算。

初次驱动的复查曾因本地调用额度中止，原始失败记录保留。继续评测时，对已经成功的三条相同复核请求进行了逐字匹配并复用原响应，没有重复请求服务器，也没有改写模型结果。最后的“源码未变化复查”则是插件自身正常跳过，两者是不同机制。

表中的时间是实际 HTTP 调用时间之和，包含网络及本地传输桥接，不包含准备、诊断、暂停和评判时间，也不是某个 Web 会话的总等待时间。

## 结论与下一步

这轮小样本确认了真实接口可以贯通两轮审查、引用校验和增量复查，且正常代码和缺少业务信息的案例没有制造缺陷。它也暴露了过度确认、重复风险和复查噪声，**不能据此宣称稳定的准确率、召回率或生产环境质量保证**。

下一轮优先补充完整可执行的 Store 实现，让模型真正看到条件发布和版本隔离逻辑，再用新的独立案例测试。审查策略应进一步要求：缺少异常处理或回滚时，必须能指出违反哪条明确规则、由哪个可见实现产生实际损害，才能确认缺陷。复查也需要减少对未改动代码的泛化风险重复提问。

本次仅执行和记录评测，没有修改已发布插件的核心逻辑，没有重新发布 npm 包，也没有把结果自动发到社区。

本页是首次 0.1.1 评测的归档说明；下列原始材料位于交付的评测压缩包内，未全部复制到本源码仓库。0.2.0 新能力的验证另见 VALIDATION_0.2.0.md。

- `measured-run/results.json`：正式调用用量、各次阶段结果与失败/恢复记录。

- `runtime-results.json`：实际执行的并发、输入校验和补偿反例结果。
- `run.mjs`、`request.ps1`、`runtime-checks.mjs`：可复用评测脚本；密钥通过进程环境变量 `DSH_EVAL_DEEPSEEK_KEY` 传入。

注意：文件名相同的初次失败会话快照可能被同一案例的后续成功报告替换，阶段级失败状态仍完整保留于 results.json；HTTP 原始请求和响应未被替换。
