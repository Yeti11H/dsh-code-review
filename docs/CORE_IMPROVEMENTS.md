# 0.3.0 核心改进

日期：2026-11-16。本轮沿用现有插件架构，交付版本为 0.3.0。GitHub 预发布提供源码和安装包；npm latest 仍为 0.2.1，安装旧包不会自动获得本轮改动。完整检查与发布状态见 [0.3.0 验证记录](VALIDATION_0.3.0.md)。

## 业务依据与复查

`ReviewService.recheck(id, executeTests, signal, reviewContext?)` 保留前三个参数，新增第四个可选完整上下文。官方 `recheck` 工具新增同名可选对象，三个内部字段均必须提供。

- 不传新上下文时，沿用原规则。
- 源码和业务依据都没有变化，且不执行测试时，保留历史结果，不调用模型。
- 需求、规则或排除范围变化时，重扫原审查目标的完整改动集合，并重新核对未决问题。
- 每轮保存 `contextSnapshot` 与 `contextHash`。哈希只识别输入，不代表需求正确。
- 旧会话首次复查前，按原有单一上下文填充旧轮次的依据；不虚构不存在的需求历史。
- 更换规则后，原来的接受风险重新进入核查；误报反馈不跨上下文复用。
- 规则或范围变化本身不能作为“代码已修复”的证明。旧问题需要人工确认处置；这是保守策略，可能增加一次人工确认。
- 规则更新失败或取消时，保留最近完成轮次的结论与旧业务依据，状态为未完成/过期。重试仍使用新规则，重新分析成功后才清除过期状态。
- 旧结论尚未按新规则复查完成时，不允许将其人工处置记为新规则的反馈。

目前上下文变更由用户显式输入，不监控外部文档，也没有新增 PRD 解析或 MCP 接入。数组顺序或文字变化保守地触发重审；对象属性顺序变化不触发。

## 报告

报告顶部展示分析状态、确认/待核查/可选数量、高严重性待处理事项、测试命令执行情况和读取遗漏。后果严重性与模型核查结论单独显示；现有处理优先级算法未修改，不输出 PR 安全概率。

“人工核查交接”列出失败原因、过期输入、覆盖不足、测试失败、连续不收敛，以及需要补充依据的问题位置和验证方法。原始引用、详细推理与 JSON 历史保留。

引用匹配只说明原文存在。模型填写完整触发路径也不保证判断成立。测试命令成功不自动证明每条缺陷已复现或修复。本轮不宣称已解决真实模型过度确认或复查噪声；这需要后续固定样本对照。
