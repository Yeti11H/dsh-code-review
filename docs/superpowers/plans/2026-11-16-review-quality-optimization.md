## 2. 从研究中提炼的可验证假设

用户提供的论文题目、发表信息、百分比与适用条件尚未核对原文，暂不视为项目实证或宣传引用。

| 研究启发 | 本项目待验证的假设 | 不应作出的推论 |
| --- | --- | --- |
| AI 意见会影响人的注意力 | 分开呈现问题影响、证据状态、未覆盖范围，有助于正确核查 | 有风险评分就能发现高严重性漏报 |
| 评论噪声可能增加负担 | 复核和增量复查能减少无效意见及重复核查 | 评论少就一定更准确 |
| 上下文影响采纳与判断 | 同样代码配不同已确认规则，结论应合理变化 | 需求越长越有效，上传 PRD 就能理解业务 |
| 工作流影响使用价值 | 同编号追踪和明确交接能降低处理成本 | 多 Agent 或更多调用必然提高质量 |

论文用于解释为何选择实验，不用于证明尚未测出的收益。涉及具体研究结论的公开引用，需先核对原文、样本、模型/系统和指标定义。

## 3. 本轮产品与工程边界

保留定位：**面向 DSH 的轻量、证据驱动代码审查插件，结合用户提供的业务规则核查本次改动并跟踪修复。**

优先场景：边界明确的功能改动、提交前审查、修复后复查。权限、资金、删除等高后果改动只能辅助负责人判断。大型复杂 PR 不自动成为推荐场景，先看覆盖范围与预算。

本轮不做：多格式 PRD 平台、飞书/GitHub MCP 接入、项目代码生成、云端知识库、组织权限、自动合并、手机适配、正式桌面产品化。独立浅色工作台仍是交互原型，其预设修复与复查不能用作真实结果证据。

### 全局约束

- 不替换现有框架，不增加运行时数据库或检索库。
- 四个现有工具名称保持不变；旧调用参数继续可用。
- 0.2.1 旧会话可读，新字段可选，缺失时保守解释。
- 代码原文匹配、模型路径判断、实际测试执行分别呈现。
- 不能通过忽略高风险问题、删样本或降低规则强度来获得更好评测。
- 不在评测器中执行被审代码；独立验收脚本仅针对受控本地样例运行。
- 默认不向外部 PR 评论、不上传视频、不运行真实付费接口。
- 不修改已有 API 凭据，不在命令、录像、报告或公共产物中泄露密钥。

## 6. 详细任务

### 任务 1：固定案例与评判协议

**文件：** 新增 examples/evaluation/、docs/EVALUATION_PROTOCOL.md、tests/evaluation.test.mjs。

**输入/输出：** 案例记录包含 id、family、split、provenance、sourceFiles、context、snapshotHash；标签独立存放，不出现在模型请求中。provenance 区分真实历史问题、人工构造与已有归档。

- [ ] 盘点三个旧评测案例、分页 Web 案例、修复前后版本和现存反例，记录哪些可复用；旧案例列为开发样本，不冒充未见测试集。
- [ ] 规划 6 类业务场景、每类 3 个条件，共 18 条探索案例：缺陷成立、明确规则下合理实现、业务信息不足。场景包含输入边界、角色权限、发布顺序、失败补偿约定、重试幂等、状态迁移/删除范围。
- [ ] 每条标签写清适用规则、实际影响、可见保护措施、缺失信息，以及允许的正确回答；“信息不足”不要求整份报告必须为空。
- [ ] 至少保留一组源码与改动完全相同、只改变适用规则的对照，例如上限 100 与任意正整数两种分页约定。该组置于同一 family/split，单独统计结论是否随规则变化。
- [ ] 为可执行缺陷和正确对照写独立运行断言；这些断言不提供给审查模型，不由审查结果反向生成。
- [ ] 按场景族划分 2 族开发样本、4 族保留测试样本，即 6 条开发、12 条保留。相关代码、修复版本、规则变体留在同一分组。若开发者已用某题调试策略，该题移入开发集并补独立测试题。
- [ ] 先写离线检查：模型输入不包含 labels/答案；哈希变化报错；开发/测试 family 不重叠；来源字段缺失失败。
- [ ] 本地验证受控样例行为，确认标签有独立依据。标签由维护者确认；如仅由 AI 辅助复核，记录这一限制，不称独立专家盲审。

**验收：** 18 条案例、分组和答案可检查；无虚构历史缺陷；任何模型请求都不包含评判答案。小样本仅用于探索，不宣称统计上代表所有仓库。

### 任务 2：建立三组对照与资源记录

**文件：** 新增 scripts/evaluation/*.mjs，扩展 tests/evaluation.test.mjs；复用 src/services/deepseek-model.ts、GitService、ReviewService。

**接口提案：** `runCase({caseId, arm, runId, config})`，arm 为 `code-only`、`with-requirements`、`plugin`；返回运行记录路径和成功/失败状态。`scoreRun(runDirectory, adjudicationsPath)` 仅汇总已裁定标签，不自动假定模型自评正确。

- [ ] A 组：模型直接审查固定代码；B 组：同样代码，加同样业务规则；C 组：现有插件流程，加同样业务规则。
- [ ] 三组使用同一个模型服务、同样的请求模型标识、代码快照、文件集合和文本窗口；B/C 的业务规则与范围完全相同。配置记录包含代码/上下文/提示词哈希和包提交。
- [ ] 提供一致的结果字段要求，不以是否带稳定编号等产品格式优势冒充缺陷识别优势。B/C 的区别限定为待比较流程和提示词组织；不声称单独证明某个内部机制。
- [ ] 给测试用的固定代码包设置总量限制，保证各组均可看到全部案例材料；如果 C 组额外读取相关上下文，应显式记为暴露差异，补匹配输入对照或停止因果归因。
- [ ] 各组设同一每案例总输出 token 上限与超时；记录实际调用次数、阶段、输入/输出 tokens、模型返回标识、墙钟耗时及失败。单次调用预算和整个流程预算分别记录。
- [ ] 全流程达到总 token/调用上限时停止并记录不完整结果；不跳过、重试到满意或将失败计为“无问题”。仅在协议预先规定的网络故障条件下有限重试，并保留所有尝试。
- [ ] 用本地脚本模型/HTTP 测试服务验证三条路径、超时、无效 JSON、429/5xx、预算耗尽、重复 runId 和答案隔离；这些运行标记为工程测试。
- [ ] 提供仅检查配置和预计请求规模的 dry-run。真实预算以实际价格、路由、缓存条件和用户同意的金额上限为准；本计划不默认授权付费。

请求规模说明：3 条试跑乘 3 组是 9 次“审查运行”；12 条保留测试乘 3 组是 36 次审查运行。一次插件审查可能包含多次模型请求，因此二者不能等同于 9 次或 36 次 API 请求。先执行经授权的小规模试跑，根据实际用量决定是否继续完整评测，不一次启动全部组合。

**验收命令提案：** `npm run build` 后，`node --test tests/evaluation.test.mjs`；`node scripts/evaluation/run.mjs --dry-run --split dev` 不调用外部模型。命令在未来实现后才可用，本轮未执行。

### 任务 3：让报告帮助核查，而非增加信心错觉

**文件：** 修改 reporter.ts、shared.ts（仅在结果映射确有需要时）、相关测试；保留 risk.ts 分数算法，避免同轮同时改评分和审查策略。

**接口：** 保留 ReviewResult 与四工具现有字段。报告摘要从当前会话事实生成，不新增模型主观“置信度百分比”。

- [ ] 先补报告回归：高严重性但 needs_check、代码引用匹配但未执行测试、测试失败、空结果但有遗漏、旧会话缺少新字段。
- [ ] 报告顶部简明展示：本轮完成情况、待处理数量、优先核查事项、测试是否执行、覆盖不足和下一步。详细引用与调用过程继续保留在后文。
- [ ] 在问题层面分开呈现后果严重性、核查结论、原文匹配和运行证据；没有逐问题复现记录时，不因一次项目测试通过就标 executed_test。
- [ ] 保留 0–10 为处理优先级；不称 PR 安全总分、不用多个低风险项稀释高风险项，也不将零分解释成可合并。
- [ ] 高严重性待核查项指出缺什么信息和需要核实哪个路径。缺少具体结论时使用真实 limitations，不编造业务原因。
- [ ] 人工接手时列出现有未决问题、已知触发条件、缺失依赖与停止原因；区分连续不收敛、覆盖不足、测试失败和快照过期。
- [ ] 文本压缩不得隐藏尚未核查的高后果问题，或用删意见获得更好的“噪声”数字。

**验收：** JSON 与 Markdown 状态一致，模型工具结果不会把分析完成写成批准合并；受控报告渲染检查通过，原始详细记录仍可追溯。

### 任务 4：业务规则变化也能正确触发复查

这是现有接口的明确增量：目前 recheck 只接受会话与是否运行测试，用户更新规则不能直接并入原会话。若暂不做此增量，必须文档明确“规则变化请新建审查”，不能宣传自动失效已实现。

**文件：** types.ts、reviewer.ts、tools/recheck.ts、reporter.ts 与 integration/harness 测试。

**接口提案：** `recheck(id, executeTests = false, signal?, reviewContext?: ReviewContext)`，通过第四个可选参数保持现有调用兼容；工具新增可选对象 `reviewContext`，包含完整 requirement、businessRules、outOfScope，采用整对象替换而非隐式部分合并。

**数据提案：** ReviewRound 新增可选 `contextSnapshot?: ReviewContext` 与 `contextHash?: string`；session.context 表示当前接受的上下文，旧轮次原始需求保留。不得在原对象上就地改写历轮需求。

- [ ] 先写失败回归：代码未变但规则由“允许任意正整数”改为“上限 100”，必须重新审查；同样代码及规则、无测试请求时仍零调用跳过。
- [ ] 上下文变化时重扫本次审查目标的完整改动集合，并重新核对未决旧问题，不只检查代码增量。移出范围的旧问题不凭范围变化自动标 resolved，交接给人处置。
- [ ] 旧记录缺少逐轮上下文时，只能在没有发生变更前用原 session.context 回填其当时上下文；记录兼容迁移，不凭空还原未知历史。
- [ ] 确认规则变化后旧反馈因 contextHash 不同失效；wont_fix 不能作为安全证明，也不因新输入静默改为已修复。
- [ ] 模型失败、取消和校验失败不留下被误认为有效的新结论；报告应同时标明最新需求及最近成功分析所对应的旧需求。
- [ ] 覆盖行号移动、问题重现、依赖文件变化和不同代码版本三轮接手；已有稳定编号、旧参数、显式测试审批行为继续通过。
- [ ] 更新工具参数说明，提示传新规则代表用户更换本轮依据，外层 Agent 不应自行补写未确认业务规则。

**验收：** 规则变化时不错误复用旧结论；历史可追溯；无变化跳过仍有效；不能仅靠哈希相等声称业务正确。

### 任务 5：真实对照与有依据的策略调整

**文件：** 评测结果先写仓库外的受控运行目录；人工判定后更新 docs/EVALUATION_RESULTS.md，必要时针对性修改两处 prompts 与 evidence.ts。

- [ ] 用户确认可用模型和付费总预算后，只在开发集选 3 条做连通/预算试跑；记录请求模型与实际返回模型，无法固定服务版本时说明可重复性限制。
- [ ] 在修改影响模型行为的逻辑前记录 0.2.1 基线，对照代码提交固定。先比较 A/B/C，观察问题究竟来自缺上下文、检索窗口、核查策略还是输出转述。
- [ ] 使用开发集调整过度确认与复查噪声。缺少回滚/事务不自动成立；提示词已有同类要求时，先检查反例与上下文可见性，不只堆更多禁令。
- [ ] 程序校验只能检查结构、来源、原文和预算；字段齐全不能作为语义正确的证明。不能用关键词分类器冒充业务缺陷裁判。
- [ ] 保留当前修复后的复查与旧版本过度确认案例。消重只能合并同一触发机制，不只看文件、类别或相似标题，避免隐藏两个独立缺陷。
- [ ] 冻结策略后，保留集按预先固定顺序/配置完成一轮三组对照。保留集不用于调提示词；若被用于修正，改列开发集，后续补新测试集。
- [ ] 独立评判答案与真实触发断言核对每条发现。人工裁定时尽量隐藏组别；没有独立评审人就明确标为维护者评判，不声称双盲。
- [ ] 模型有随机性，小样本一次运行不足以声称稳定提升；预算允许时预先约定重复次数，保留全部结果，禁止只展示最好的一次。

**指标定义：**

- 确认意见精确率：人工判定成立的 confirmed / 全部待处理 confirmed；分母为零标 N/A。
- 已知缺陷发现率：被正确定位的预置缺陷 / 独立标签中的已知缺陷；needs_check 另列，不能直接充当确认检出。
- 不确定性错误：信息不足案例被强行确认为缺陷的数量。
- 复查表现：同一问题稳定追踪、误关闭、问题重现漏开、新增无关意见，分别统计。
- 人工成本：用户核实意见的实际耗时；没有真人试用时标未测，不用模型回复长度代替。
- 资源：逐案例调用次数、tokens、延迟及中位数/尾部表现；样本不足时给原始值/最大值，账单不明确不虚报金额。
- 按场景与影响等级展开逐题差异，不仅报告均值。程序“确认”与人工认定真实缺陷保持分列。

**继续门槛：** 确定性工程行为全部符合验收；对插件优于 B 组的主张必须存在对应数据。若没有清晰增益，交付原始结果和失败分析，暂停扩大功能范围。不得把拟定百分比目标写成已有成绩。
